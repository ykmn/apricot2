# Ускорение AD-логина

## Проблема

Логин через LDAP (`app/auth.py`, `_authenticate_one_domain()`) ощущается медленным.
Разбор кода показал два источника лишнего времени, оба не связаны с
разрешением вложенных групп (оно уже эффективно — см. ниже):

1. `ldap3.Server(server_url, get_info=ldap3.ALL, connect_timeout=5)` —
   при **каждом** логине заставляет ldap3 забрать с DC полную живую схему
   AD (RootDSE + сотни атрибутов/классов объектов). Это обычно самая
   тяжёлая сетевая операция во всём цикле логина и никак не зависит от
   того, сколько у пользователя групп или насколько глубоко они вложены.
2. `_get_primary_group_dn()` делает отдельный LDAP-поиск
   (`primaryGroupToken=...`) на каждый логин, чтобы перевести
   `primaryGroupID` (RID) в DN основной группы пользователя. Эта связка
   RID → DN группы в домене практически никогда не меняется между
   логинами.

**Вложенные группы уже резолвятся правильно и быстро** —
`_get_transitive_groups()` использует AD-расширение
`LDAP_MATCHING_RULE_IN_CHAIN` (OID `1.2.840.113556.1.4.1941`), которое
разворачивает всю цепочку вложенности на стороне сервера одним запросом.
Это и есть рекомендованный быстрый способ для AD — трогать его не нужно.

## Решение

Две точечные правки в `app/auth.py`, без изменения структуры соединений
(сервисный бинд + отдельный ре-бинд паролем пользователя остаются как
есть) и без изменения обработки вложенных групп/multi-domain перебора.

### 1. Схема AD — офлайн-профиль вместо живого запроса

```python
server = ldap3.Server(server_url, get_info=ldap3.OFFLINE_AD_2012_R2, connect_timeout=5)
```

`OFFLINE_AD_2012_R2` — встроенный в ldap3 статический дамп реальной схемы
AD 2012 R2. Он даёт то же самое форматирование атрибутов (включая
`primaryGroupID`), что и live-схема через `get_info=ldap3.ALL`, но без
единого сетевого запроса к DC. Правка в одном месте — этот `Server(...)`
используется и для двухфазного пути (сервисный аккаунт), и для
однофазного (NTLM-бинд без `bind_secret`).

### 2. Кеш RID → DN основной группы

Module-level кеш в `auth.py`:

```python
_primary_group_dn_cache: dict[tuple[str, int], tuple[str, float]] = {}
_PRIMARY_GROUP_CACHE_TTL = 3600  # 1 час
```

`_get_primary_group_dn(conn, base_dn, primary_group_id)`:
- ключ `(base_dn, int(primary_group_id))`;
- при попадании и `time.time() - cached_at < TTL` — вернуть закешированный
  DN без LDAP-запроса;
- при промахе/истечении — выполнить существующий поиск
  `(primaryGroupToken=...)`, как сейчас, и на успехе записать в кеш;
- отрицательный кеш (когда группа не найдена) не нужен — редкий случай,
  не стоит усложнять.

Кеш не персистится на диск и не инвалидируется при `invalidate_auth_cache()`
— переживать перезапуск процесса не критично (домен настолько часто не
меняется), а сам ключ включает `base_dn`, так что смена конфигурации домена
естественным образом не даёт коллизий.

## Тестирование

Автотестов в проекте нет (см. `CLAUDE.md`). Проверка — реальный логин на
боевом AD, доступ к которому есть у пользователя:

1. Замерить время `_authenticate_one_domain()` до правок (добавить временный
   `time.perf_counter()` вокруг вызова в debug-лог).
2. Применить обе правки, повторить логин тем же пользователем — сравнить
   время и подтвердить, что набор групп (`is_admin`, лог транзитивных
   групп) идентичен варианту до правок.
3. Повторный логин в течение часа — убедиться по debug-логу, что поиск
   `primaryGroupToken` больше не выполняется (кеш-хит).
4. Проверить логин пользователя из другого домена (если сконфигурирован
   multi-domain) — оба домена используют один и тот же кешируемый путь
   независимо (разный `base_dn` → разные ключи кеша).

## Не входит в объём

- Пул/переиспользование LDAP-соединений между логинами (объединение
  сервисного бинда и проверки пароля через `conn.rebind()` и т.п.) —
  осознанно отложено: пользователь выбрал минимальный по риску вариант.
- Изменение алгоритма разрешения вложенных групп — уже оптимален.
